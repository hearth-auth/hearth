# Getting Started with Hearth

**Goal:** First authenticated request in your app. **Time:** ~5 minutes.

**Prerequisites:** `docker` and a package manager for your stack (`npm` / Go toolchain / `pip`). For the setup steps you also need `curl` and `jq`.

:::tip[SDK reference]
Step 3 adds browser login with the TypeScript SDK; step 4 checks permissions from TypeScript, Go, and Python backends. For deeper coverage — RBAC hooks, middleware patterns, and the Admin API — see the [SDK overview](/docs/sdks/overview).
:::

---

## 1. Run Hearth

**From source (recommended)** — no Docker required; works on Linux, Mac, and Windows:

```bash
cargo run --features dev-endpoints -- serve --dev
# or:  make dev
```

**Docker on Linux** — `--network=host` gives the container access to the host's loopback, which `--dev` requires:

```bash
docker run --rm --network=host ghcr.io/hearth-auth/hearth:latest serve --dev
```

> **Known gap — the image is not anonymously pullable today.** Re-checked 2026-09-21: an
> unauthenticated manifest fetch for `ghcr.io/hearth-auth/hearth` returns **401** for every tag,
> so the command above fails before it starts. Run `docker login ghcr.io` with a token carrying
> `read:packages`, or use the from-source path above — it needs no Docker and is the recommended
> route anyway — or the signed release binaries ([README → Install](../../README.md#install)).
> The Helm chart (`oci://ghcr.io/hearth-auth/charts/hearth`) is private for the same reason.
> Still private when re-checked for the 2026-09-28 GA audit. Tracked as remediation task 3.4.

> **Docker on Mac / Windows:** `--network=host` is not equivalent to the host loopback on Docker Desktop, so `--dev` cannot bind correctly in a single container. Use the Docker Compose stack instead — see [`deploy/README.md`](../../deploy/README.md). Note that the Compose stack does not expose the `--dev` bootstrap endpoint; set up your first realm via the Admin API.

`--dev` uses a throwaway data directory, enables the bootstrap endpoint (only in a binary built with the opt-in `dev-endpoints` cargo feature — `make dev` and the command above are; the published container image and a plain `cargo build` are not, and log a warning saying so), and starts the built-in **mailcatcher** (captured email at `http://127.0.0.1:8420/dev/mail`). With a bare `cargo run --features dev-endpoints -- serve --dev`, **data does not persist across restarts** — the store lives in a temp directory removed on exit. `make dev` is different: it sets `HEARTH_DEV_DATA_DIR=./data/dev`, so that store *does* survive restarts; `make dev-reset` wipes it.

Confirm it is up:

```bash
curl -fsS http://127.0.0.1:8420/readyz
# → {"status":"ready","storage":"ok"}
```

:::tip[Production deployment]
For Docker Compose, systemd, or Helm, see [`deploy/README.md`](../../deploy/README.md).
:::

## 2. Bootstrap a realm and register your app

Create a dev realm with an admin token, then register a public OAuth client for your app. Both are one-time **setup** — not application code.

```bash
# Create the dev realm + an admin token
BOOTSTRAP=$(curl -fsS -X POST http://127.0.0.1:8420/admin/bootstrap)
REALM_ID=$(echo "$BOOTSTRAP" | jq -r .realm_id)
ADMIN_TOKEN=$(echo "$BOOTSTRAP" | jq -r .access_token)

# Register a public client (no secret — PKCE secures it)
CLIENT_ID=$(curl -fsS -X POST http://127.0.0.1:8420/clients \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "X-Realm-ID: $REALM_ID" \
  -H "Content-Type: application/json" \
  -d '{"client_name":"quickstart","redirect_uris":["http://localhost:3000/callback"]}' \
  | jq -r .client_id)

echo "REALM_ID:  $REALM_ID"
echo "CLIENT_ID: $CLIENT_ID"
```

Your app (step 3) needs three values: the **realm slug** — `dev-realm` in `--dev` mode — the **`CLIENT_ID`** printed above, and the server URL `http://localhost:8420`.

:::warning[Dev-only endpoint]
`/admin/bootstrap` returns `404 Not Found` outside `--dev` mode. In production, create realms and register clients via `hearth.yaml` or the Admin API — never bootstrap.
:::

## 3. Add login to your app

Logging a user in is the OAuth 2.0 authorization-code + PKCE flow: send the user to Hearth to authenticate, then exchange the returned `code` for tokens on your callback route. The TypeScript SDK uses the `createHearthAuth` browser facade; every server SDK uses `beginLogin` to build the redirect URL and `completeLogin` to exchange the code. Every tab uses the realm slug `dev-realm`, the `CLIENT_ID` from step 2, redirect URI `http://localhost:3000/callback`, and server `http://localhost:8420`.

```ts
const p = new URLSearchParams(window.location.search);
```

**Login route** — generate PKCE and redirect to Hearth:

```ts
import { HearthClient } from '@hearth-auth/sdk';
import { Router } from 'express';

const client = new HearthClient({
  issuerUrl: 'http://localhost:8420',
  realmId:   '<realm-id>',
  clientId:  '<client-id>',
});

const router = Router();

router.get('/login', async (req, res) => {
  const result = await client.beginLogin('http://localhost:3000/callback', 'openid');
  // Store PKCE values server-side — never expose codeVerifier to the browser
  req.session.oauthState   = result.state;
  req.session.codeVerifier = result.codeVerifier;
  res.redirect(result.authorizationUrl);
});
```

**Callback route** — check `state`, then exchange the code for tokens:

```ts
router.get('/callback', async (req, res) => {
  if (req.query.state !== req.session.oauthState) {
    return res.status(400).send('state mismatch');
  }
  const tokens = await client.completeLogin(
    req.query.code as string,
    req.session.codeVerifier,
    'http://localhost:3000/callback',
  );
  req.session.accessToken = tokens.access_token;
  res.redirect('/dashboard');
});
```

```ts
export async function GET() {

    `${process.env.NEXT_PUBLIC_APP_URL}/auth/callback`,

  );
```

**Callback route handler** (`app/auth/callback/route.ts`):

```ts
import { NextResponse, type NextRequest } from 'next/server';
import { client } from '@/lib/hearth';

export async function GET(request: NextRequest) {
  const params   = request.nextUrl.searchParams;
  const state    = request.cookies.get('oauth_state')?.value;
  const verifier = request.cookies.get('code_verifier')?.value;
  if (!state || !verifier || params.get('state') !== state) {
    return NextResponse.json({ error: 'state mismatch' }, { status: 400 });
  }
  const tokens = await client.completeLogin(
    params.get('code')!,
    verifier,
    `${process.env.NEXT_PUBLIC_APP_URL}/auth/callback`,
  );
  const response = NextResponse.redirect(new URL('/dashboard', request.url));
  response.cookies.set('access_token', tokens.access_token, {
    httpOnly: true, secure: true, sameSite: 'lax', path: '/',
  });
  response.cookies.delete('oauth_state');
  response.cookies.delete('code_verifier');
  return response;
}
```

The access token is signed with your realm's Ed25519 key, and its `permissions` are resolved at issue time — checking them needs no network call (step 4).

:::tip[Browser vs server]
The TypeScript SDK ships `createHearthAuth` — a **stateful browser facade** that stores tokens in `sessionStorage` and handles silent refresh. For server code, `HearthClient` in the same package — and every other SDK (Go, Python, PHP) — ships **stateless** `beginLogin`/`completeLogin` helpers: `beginLogin` returns the values you persist in your session, `completeLogin` exchanges the code. See the [`full-stack-demo`](https://github.com/hearth-auth/hearth/tree/main/examples/full-stack-demo) for a complete Vite + React + Go example.
:::

:::note[Node server handling the callback?]
If your Node.js server owns the OAuth callback route (Next.js API routes, Express, Fastify), use `client.beginLogin()` / `client.completeLogin()` from `@hearth-auth/sdk` — see the Node.js tab above and the [TypeScript SDK guide](/docs/sdks/typescript#server-side-nodejs). For browser-hosted login (React SPA, Next.js client components), use the TypeScript tab.
:::

## 4. Protect a route in your app

Fetch Hearth's public signing keys from the JWKS endpoint and verify incoming Bearer tokens cryptographically. The Hearth SDKs provide middleware for the most common frameworks.

The following examples guard a route and check that the caller has the `hearth.admin` permission.

```tsx
// Reads permissions from the JWT in context — no network call.
```

```python
from hearth import HearthClient

def require_permission(permission: str):
    """Generic dependency — checks permission from the JWT claim set."""
    def check(authorization: str):
        token = authorization.removeprefix("Bearer ")
        if not HearthClient.has_permission(token, permission):

        return token
    return check
```

```python
from functools import wraps
from flask import request, abort, g
from hearth import HearthClient

client = HearthClient(base_url=os.environ['HEARTH_BASE_URL'], realm_id=os.environ['HEARTH_REALM_ID'])

def require_permission(permission: str):
    def decorator(f):
        @wraps(f)
        def wrapped(*args, **kwargs):
            token = request.headers.get('Authorization', '').removeprefix('Bearer ')
            claims = client.verify_token(token)
            if not claims.has_permission(permission):
                abort(403)
            g.hearth_claims = claims
            return f(*args, **kwargs)
        return wrapped
    return decorator

@app.route('/admin/data')
@require_permission('hearth.admin')
def admin_data():
    return {'sub': g.hearth_claims.sub}
```

The local RBAC checks — `useHasPermission` (TypeScript), `HasPermission` (Go), `has_permission` (Python) — read the `permissions` array embedded in the token at issue time by Hearth's RBAC engine, with no network call. The `verifyToken()` calls (Node.js, PHP) and `hearthMiddleware` additionally validate the token's Ed25519 signature against the realm's cached JWKS before the check.

Prefer no SDK? Verify tokens directly against the realm's JWKS endpoint — see [Token verification without an SDK](/docs/sdks/overview#token-verification-without-an-sdk).

For browser SPA and BFF token-storage patterns, see [Browser / SPA token handling](browser-spa-tokens.md).
