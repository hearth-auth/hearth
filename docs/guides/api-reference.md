# Using the Hearth OpenAPI Spec

**Who this is for:** Integrators building against the Hearth REST API, and contributors
who add or change HTTP endpoints.

**Prerequisites:** A running Hearth server (see [Getting Started](getting-started.md)) or the
static spec files in `docs/api/`.

---

## Where the spec lives

Hearth ships two source files and one merged output:

| File | What it is |
|------|-----------|
| `docs/api/openapi.proto-derived.json` | Swagger 2.0 snapshot auto-generated by `buf generate` from `.proto` service definitions. Source of truth for every gRPC-backed HTTP route. |
| `docs/api/openapi.supplement.yaml` | Hand-written OpenAPI 3.1 YAML covering routes that have no proto service definition (admin bootstrap, OIDC discovery, Swagger UI endpoints, etc.). |
| `docs/api/openapi.json` | **The merged output.** `scripts/merge_openapi.py` combines the two sources above into a single OpenAPI 3.1 JSON document. This is the file to import into API clients. |

All three files are committed to the repo. `docs/api/openapi.json` is embedded in the
binary at compile time, so a running Hearth server can serve it directly.

### Live endpoints (running server)

| Endpoint | Content |
|----------|---------|
| `GET /openapi.json` | Merged OpenAPI 3.1 JSON (same content as `docs/api/openapi.json`) |
| `GET /openapi.yaml` | Supplement-only OpenAPI 3.1 YAML (`openapi.supplement.yaml`) |
| `GET /docs` | Swagger UI browser, loading the spec from `/openapi.json` |

```bash
# Browse the API interactively (start Hearth first)
make dev
open http://127.0.0.1:8420/docs
```

## Import into an API client

### Postman

1. Open Postman → **Import** → **Link**.
2. Enter `http://127.0.0.1:8420/openapi.json` (or the URL of your deployed Hearth instance).
3. Select **OpenAPI 3.0** and click **Import**.

Alternatively, import the file directly:
**Import** → **File** → select `docs/api/openapi.json`.

### Bruno

```bash
# From the Bruno collection root
bru import openapi --input docs/api/openapi.json --output collections/hearth
```

Or use **Import Collection** → **OpenAPI v3** from the Bruno desktop app and point it at
`docs/api/openapi.json`.

### Insomnia

1. **New Collection** → **Import** → **From File**.
2. Select `docs/api/openapi.json`.
3. Insomnia detects OpenAPI 3.1 automatically.

## Serve Swagger UI offline (no running Hearth required)

If you need a spec browser without a live Hearth server:

```bash
docker run --rm -p 8080:8080 \
  -e SWAGGER_JSON=/spec/openapi.json \
  -v "$(pwd)/docs/api:/spec:ro" \
  swaggerapi/swagger-ui
```

Open `http://localhost:8080`.

## Generate a typed client

### Go — `oapi-codegen`

```bash
go install github.com/deepmap/oapi-codegen/v2/cmd/oapi-codegen@latest

oapi-codegen \
  --config=oapi-codegen.yaml \
  docs/api/openapi.json

# Minimal oapi-codegen.yaml:
# package: hearthapiClient
# generate:
#   client: true
#   models: true
# output: hearth_client.gen.go
```

### TypeScript / JavaScript — `openapi-generator`

```bash
npx @openapitools/openapi-generator-cli generate \
  -i docs/api/openapi.json \
  -g typescript-fetch \
  -o src/generated/hearth-api \
  --additional-properties=supportsES6=true,withSeparateModelsAndApi=true
```

### Any other language — `openapi-generator-cli`

```bash
# List supported generators
npx @openapitools/openapi-generator-cli list

# Example: Python client
npx @openapitools/openapi-generator-cli generate \
  -i docs/api/openapi.json \
  -g python \
  -o hearth-python-client
```

## Keep the spec current

### When you change a `.proto` file

The proto-derived spec is regenerated as part of the normal proto workflow:

```bash
make proto-gen   # regenerates SDK types + openapi.proto-derived.json
make openapi     # merges proto-derived.json + supplement.yaml → openapi.json
```

Both steps are wired together — run `make proto-gen && make openapi` after any `.proto`
change and commit the updated `docs/api/openapi.json`.

The pre-commit hook runs `make proto-gen` automatically when `.proto` files are staged.
`make openapi` is **not** run by the hook — run it manually and stage
`docs/api/openapi.json` before committing.

A CI gate (`make openapi-check`) fails the build if `docs/api/openapi.json` is stale
relative to its sources.

### When you add a route with no proto definition

Edit `docs/api/openapi.supplement.yaml` and add your path using standard OpenAPI 3.1
syntax. Supplement paths take precedence over proto-derived paths when both files define
the same route.

```yaml
# docs/api/openapi.supplement.yaml — excerpt
paths:
  /admin/bootstrap:
    post:
      summary: Bootstrap a realm and admin user (dev mode only)
      tags: [admin]
      responses:
        "200":
          description: Bootstrap response
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/BootstrapResponse"
```

After editing the supplement, run `make openapi` to regenerate `docs/api/openapi.json`.

### Drift gate

`tests/openapi.rs` contains a parity test that verifies every expected Axum route
appears in the merged spec. The test list must be kept in sync with the route table in
`src/protocol/http.rs`. Run it with:

```bash
cargo nextest run --test openapi
```

## Files at a glance

```
docs/api/
├── openapi.json               # Merged output — import this into clients
├── openapi.proto-derived.json # Auto-generated from .proto files (buf generate)
├── openapi.supplement.yaml    # Hand-written paths (no proto definition)
└── grpc-only.txt              # gRPC-only methods excluded from HTTP/REST surface

scripts/
└── merge_openapi.py           # Merges proto-derived + supplement → openapi.json
```
