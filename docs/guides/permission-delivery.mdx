# Permission-delivery modes

Hearth supports three modes that control how permissions are delivered to resource servers. Each is a different point on the **latency vs consistency** spectrum.

## Quick-choice guide

| Scenario | Recommended mode |
|----------|-----------------|
| Most services — fast and scalable | `embedded` (default) |
| Post-issuance role changes must take effect immediately | `decision` |
| Stateless resource server that delegates trust | `introspection` |
| Offline token validation / mobile clients | `embedded` |

## Decision tree

```
Is sub-second permission freshness required?
├── No  → embedded (default)
└── Yes → Is the service stateful (can it call Hearth per request)?
           ├── Yes → decision
           └── No  → introspection
```

## Latency tradeoff

| Mode | Hot path latency | Permission freshness |
|------|-----------------|---------------------|
| `embedded` | 0 ms — JWT decoded locally | Stale until token expires (default 15 min) |
| `introspection` | +5–15 ms — one network call to Hearth | Fresh on each introspect call |
| `decision` | +5–15 ms — one network call to Hearth | Real-time |

## Mode details

### `embedded` (default)

Hearth resolves the user's effective roles, groups, and permissions at token issuance time and embeds them as JWT claims (`roles`, `groups`, `permissions`). Resource servers decode the JWT locally — no network call.

**Token payload excerpt:**
```json
{
  "sub": "user_01HXYZ...",
  "permissions": ["docs.view", "docs.edit"],
  "roles": ["docs-admin"],
  "groups": ["leads"],
  "exp": 1700000900
}
```

### `introspection`

The JWT carries only identity claims (`sub`, `tid`, etc.). Resource servers call `POST /realms/{realm}/introspect` with the bearer token to get the live RBAC claim set.

**Introspection call:**

<Tabs groupId="lang">
<TabItem value="ts" label="TypeScript" default>

```typescript
import { HearthClient } from '@hearth-auth/node';

const client = new HearthClient({
  issuer_url:    process.env.HEARTH_ISSUER_URL!,
  client_id:     '<resource-server-client-id>',
  client_secret: '<secret>',
});

const result = await client.introspect(rawBearerToken);
if (!result.active) return res.status(401).end();
if (!result.permissions?.includes('docs.edit')) return res.status(403).end();
```

</TabItem>
<TabItem value="go" label="Go">

```go
import hearth "github.com/hearth-auth/hearth/sdks/go/hearth"

result, err := client.Introspect(ctx, accessToken)
if err != nil || !result.Active {
    http.Error(w, "Unauthorized", http.StatusUnauthorized)
    return
}

    if p == "docs.edit" { hasDocsEdit = true; break }
}
if !hasDocsEdit {
    http.Error(w, "Forbidden", http.StatusForbidden)
    return
}
```

Hearth includes RBAC claims in introspection responses **only** when the requesting client has `access_token_authorization: introspection` configured. See [Configuring the mode](#configuring-the-mode).

### `decision`

The JWT carries only identity claims. Resource servers call `POST /oauth/authorize` with the bearer token and the required permission. Hearth evaluates the permission in real time and responds with `allowed: true/false`. Fail-closed: network errors return `false`.

**Decision call:**

## Refresh-token revocation caveat

In `embedded` mode, revoking a session or role takes effect only after the access token expires (default 15 minutes). If you need immediate revocation:

- Use `decision` or `introspection` mode on affected clients, or
- Shorten the access token TTL (`access_token_ttl` in client config), or
- Use the session-version revocation mechanism (Kotlin SDK: `SessionVersionCache`; Node/Go: subscribe to `session_revoked` webhooks and maintain a local blocklist).

## Configuring the mode

Set `access_token_authorization` when registering or updating a client via the Admin API.

**Register a new client with `decision` mode:**
```bash
curl -X POST http://127.0.0.1:8420/admin/clients \
  -H "Authorization: Bearer <admin-token>" \
  -H "X-Realm-ID: <realm-uuid>" \
  -H "Content-Type: application/json" \
  -d '{
    "client_name": "Docs Service",
    "redirect_uris": ["https://docs.example.com/callback"],
    "grant_types": ["authorization_code"],
    "access_token_authorization": "decision"
  }'
```

**Update an existing client to `introspection` mode:**
```bash
curl -X PATCH http://127.0.0.1:8420/admin/clients/<client-id> \
  -H "Authorization: Bearer <admin-token>" \
  -H "X-Realm-ID: <realm-uuid>" \
  -H "Content-Type: application/json" \
  -d '{ "access_token_authorization": "introspection" }'
```

Valid values: `"embedded"` (default), `"introspection"`, `"decision"`.

Existing clients without an explicit mode default to `"embedded"` for full backward
compatibility.

## Keycloak comparison

| Keycloak concept | Hearth equivalent |
|-----------------|-------------------|
| Realm roles in JWT | `embedded` mode — `roles` claim |
| UMA/RPT token | `decision` mode — per-request `POST /oauth/authorize` |
| Token introspection (RFC 7662) | `introspection` mode — `POST /realms/{realm}/introspect` |
| Fine-grained authorization (FGA) | `decision` mode with Hearth's permission string model |

## Org-scoped permission checks

When a user is acting in an org context, include `org_id` in the token request to scope permissions to that organization:

```bash
# Token request with org context
curl -X POST http://127.0.0.1:8420/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=authorization_code&code=<code>&org_id=org_<uuid>"
```

The resulting token's `permissions` claim reflects only org-scoped assignments for that organization plus any realm-scoped assignments. The `oid` claim is set to the org ID.
