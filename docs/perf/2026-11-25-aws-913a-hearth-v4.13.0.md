This report gives Hearth's results from the #913 AWS session 913a (2026-11-24 and 2026-11-25). #913 compares Hearth with other self-hosted identity servers on the same hardware. That comparison is in progress, and its results for the other products are not in this report: each vendor first checks its own configuration.

The session also ran the #647 restore drill at 10M users (mark 5). Its result is in [Restore drill](#restore-drill-10m-users-647-mark-5).

The rates are clean rates (see [Method](#method)). "≥" means that the 8th and last step of the ladder was clean: the ladder, not Hearth, set the limit. "Generator-bound" means that the busiest load generator used more than 300 % of its 400 % CPU at the clean step, so the generators may have set the limit.

**Findings**

1. Login scales with the vCPUs: 48/s on 2 vCPU, 192/s on 8 vCPU. [Details](#login-scales-with-the-vcpus).
2. Durable writes do not scale with the vCPUs: refresh and create user have the same clean rate at both sizes. At size 2, the failing steps fail on write-limit `503`s while p99 stays low. The cause is not known. [Details](#writes-do-not-scale-with-the-vcpus) and #937.
3. At size 2, refresh at 2,400/s and 2,800/s was clean by the step rule, but the fixed rule reports 1,600/s. [Details](#refresh-at-size-2-step-by-step).
4. Reads scale with the vCPUs, up to the top of the ladder. [Details](#reads).
5. Every `503` and `429` counts as an error, Hearth's Argon2 sheds included. This rule changed on 2026-11-24, after the first data. [Details](#rule-change-on-2026-11-24).

## Method

The method is fixed in #913. This section summarizes it.

**Ladder.** Each journey runs in two phases. The coarse phase starts at the journey's start rate and doubles the rate at each 60 s step, at most 8 steps, until the first failing step. The fine phase runs 3 steps evenly spaced between the last clean coarse step and the first failing one.

| Journeys | Start rate | Top coarse step |
|---|---|---|
| Login | 2/s | 256/s |
| Mix | 5/s | 640/s |
| Refresh, client credentials, create user | 25/s | 3,200/s |
| Userinfo, introspect, admin user lookup, cold reads | 100/s | 12,800/s |

**Each phase** is one k6 run. Before it, the seeded store is restored, the page cache is dropped, and Hearth restarts. The run starts with one warm-up minute at the phase's first rate. The warm-up is never judged. While a phase runs, the driver stops it at the first step that fails for sure (p95 above the budget, or 1 % errors).

**Clean step.** A step is clean when:

- no journey was dropped,
- errors are below 0.1 % of the finished journeys,
- p99 is within the journey's budget,
- the server stayed alive.

Every failed journey is an error, every `503` and `429` included. A clean step can therefore have a few errors: refresh at 1,600/s at size 1 had 12 `503`s (0.01 %).

**Clean rate.** The judge stops at the first failing step. The clean rate is the highest clean step before it, in either phase. A step after the first failing step does not count, even when it is clean.

**Budgets** (p99, from `cloud.sh collect`): 50 ms for userinfo, introspect, admin user lookup and the cold reads; 100 ms for refresh, client credentials and create user; 1,000 ms for login and the mix.

**Settings**

- Every write is fsynced to the write-ahead log before Hearth acknowledges it.
- HTTPS on Hearth's own listener.
- Passwords: Argon2id, m=19,456 KiB, t=2, p=1 (Hearth's default).
- Access tokens: Ed25519 JWTs, 1 hour. A reused refresh token is refused. The client credentials secret is a generated one (SHA-256 fast format).
- `PRESENT=chain`: each client presents its own newest access token, as a real client does. (The #647 rounds use `pool`.)
- Default configuration otherwise. `storage.max_writes_in_flight` is 32, its default, at both sizes.

**Journeys.** Login is the authorization code flow with PKCE through Hearth's login page. Refresh, client credentials, userinfo, introspect, admin user lookup by id and create user are one request each. The mix uses the #647 weights. The requests are those of the [v3.4.0 report](2026-10-10-aws-c7i-large.md#units). The cold reads are admin user lookups over the first 100,000 or 1M seeded users, after the page-cache drop. Admin user lookup itself uses a working set of 1,000 users. The cold reads run at size 1 only, as #913 planned.

**Once.** Each journey ran once at each size. No journey ran a second time, except login and the mix at size 1 after the rule change.

## Findings

Each finding says what was measured and what is inferred.

### Login scales with the vCPUs

**Measured.**

| Size | Clean rate | p99 | Server CPU | First failing step |
|---|---|---|---|---|
| 1 (2 vCPU) | 48/s | 278 ms | 152.5 % of 200 % | 56/s: 10.12 % `login_submit:503` |
| 2 (8 vCPU) | 192/s | 156 ms | 484.4 % of 800 % | 224/s: 3.56 % `login_submit:503` |

The clean rate is 4.0 times higher with 4 times the vCPUs. Every login error at both sizes is `login_submit:503`: the Argon2 queue refuses the password check.

**Inferred.** Login is bound by the Argon2id password check, and that work spreads over the vCPUs.

### Writes do not scale with the vCPUs

**Measured.** Refresh and create user each make durable writes. They have the same clean rate at both sizes.

| Journey | Size | Clean rate | First failing step | Errors there | p99 there | Server CPU there | Write IOPS there |
|---|---|---|---|---|---|---|---|
| Refresh | 1 | 1,600/s | 2,000/s | 0.38 % `503` | 139 ms | 144.2 % of 200 % | 702 |
| Refresh | 2 | 1,600/s | 2,000/s | 0.11 % `503` | 9.8 ms | 118.4 % of 800 % | 869 |
| Create user | 1 | 1,000/s | 1,200/s | 0.15 % `503` | 58.4 ms | 106.8 % of 200 % | 952 |
| Create user | 2 | 1,000/s | 1,200/s | 0.27 % `503` | 66.4 ms | 103.5 % of 800 % | 875 |

- The `503`s are refusals of the write limit (`storage.max_writes_in_flight`, 32): `hearth_storage_writes_shed_total` rose in each of these phases.
- At size 2, the server used 13–15 % of its CPU at these failing steps, and p99 stayed within the budget.
- At both sizes, no refresh or create user step went above 967 write IOPS, against the 3,000 IOPS of the volume.
- At size 1, refresh also saturates: at 3,200/s, p99 was 1,444 ms and 41,897 journeys were dropped, with 183 % CPU.

**Inferred, not confirmed.** At size 2, neither the CPU nor the disk's IOPS limit sets the write ceiling. The fixed write limit of 32 does: it sheds writes while p99 is low. A probable mechanism is bursts of slow gp3 fsyncs that fill the 32 permits. The cause is under investigation in #937. #911 asks a related question about a serial point; this run does not answer it for writes.

### Refresh at size 2, step by step

| Phase | Offered | Completed/s | Errors | p50 | p99 | Server CPU | Judged |
|---|---|---|---|---|---|---|---|
| coarse | 800/s | 800.0 | 0.00 % | 6.7 ms | 61.1 ms | 50.7 % | clean |
| coarse | 1,600/s | 1,600.0 | 0.00 % | 6.6 ms | 55.9 ms | 95.5 % | clean |
| coarse | 3,200/s | 3,193.6 | 0.20 % | 6.4 ms | 9.8 ms | 176.9 % | fails: errors |
| fine, warm-up | 2,000/s | 2,002.7 | 0.34 % | 6.5 ms | 10.0 ms | 114.8 % | never judged |
| fine | 2,000/s | 1,997.7 | 0.11 % | 6.5 ms | 9.8 ms | 118.4 % | fails: errors |
| fine | 2,400/s | 2,400.0 | 0.00 % | 6.5 ms | 9.2 ms | 140.6 % | after the first failing step |
| fine | 2,800/s | 2,799.8 | 0.01 % | 6.5 ms | 9.9 ms | 164.4 % | after the first failing step |

Every error is a write-limit `503`. The 2,000/s step failed with 0.11 % errors, just above the 0.1 % limit. The 2,400/s and 2,800/s steps were clean by the step rule, but they came after the first failing step. The fixed rule therefore reports 1,600/s. This report keeps that rule. The 2,400/s and 2,800/s steps show that the size 2 server can complete refreshes at those rates with p99 near 10 ms and at most 0.01 % refused writes.

### Reads

**Measured.**

- Introspect: 6,400/s at size 1, at least 12,800/s at size 2. At size 1, the step at 8,000/s used 192 % of 200 % CPU and p99 was 242 ms. At size 2, the top step used 242 % of 800 % CPU, with p99 2.2 ms.
- Userinfo: 11,200/s at size 1, at least 12,800/s at size 2.
- Admin user lookup: at least 12,800/s at both sizes. At size 1, the busiest generator used 378 % of 400 % CPU at that step (generator-bound).
- Cold reads (size 1): 11,200/s with a working set of 100,000 and of 1M users; the 1,000-user working set (admin user lookup) reached at least 12,800/s.

**Inferred.**

- At size 1, introspect is bound by the CPU: the CPU was full at the first failing step.
- The size 1 failures of userinfo and the cold reads at 12,800/s may come in part from the generators: the busiest generator used 339–393 % of 400 % CPU at that step, while the server used 106–130 % of 200 %.
- The "at least" results at size 2 are limits of the ladder, not of Hearth. Where Hearth's own limit is, is not measured.
- These runs use 1M users. They do not test #911's case (introspect with 10M users).

### Rule change on 2026-11-24

The first rule of #913 did not count Argon2 or password-hash `503`/`429` sheds as errors. Only Hearth has such a shed, so only Hearth got the exclusion. On 2026-11-24, after the first size 1 login ladder, the owner changed the rule: every `503` and `429` is an error, for every product. Login and the mix at size 1 then ran again. The results in this report use the new rule.

The first size 1 login ladder, under the old rule:

| Offered | Completed/s | `login_submit:503` | p99 | Clean by the old rule |
|---|---|---|---|---|
| 32/s | 32.0 | 0.00 % | 168 ms | yes |
| 64/s | 54.2 | 15.23 % | 466 ms | yes |
| 128/s | 54.1 | 57.70 % | 454 ms | yes |
| 256/s | 51.9 | 79.73 % | 431 ms | yes |

The old rule reported "at least 256/s", with 80 % of the logins refused. Hearth completed at most about 54 logins/s. Under the new rule, the clean rate is 48/s.

## Limits of these results

- **Per node only.** One server runs Hearth. Cluster mode is not tested.
- **The ladder and the generators.** A "≥" result is the top step of the ladder. A "generator-bound" result may be limited by the generators. Neither is Hearth's limit.
- **Step size.** The clean rate is a ladder step. The real limit is somewhere between the clean step and the first failing step.
- **One run per journey.** Each journey ran once at each size, so run-to-run variation is not measured. A step near the 0.1 % error limit can pass or fail by chance: refresh at size 2 failed at 2,000/s with 0.11 %.
- **One dataset.** 1M users in 1 realm. The #647 report has 10M-user results on an older release.
- **One disk.** EBS gp3 at 3,000 IOPS and 125 MB/s. A different disk changes the write results.
- **Default limits.** `storage.max_writes_in_flight` stayed at 32 at both sizes. A higher value may change the size 2 write results; this was not tested.

## How to run it again

The tooling is in `loadtest/compare/aws/` (revision `fcd23859` for the size 2 run). The session needs an AWS account and costs money: `compare.sh plan` prints the estimate. The driver stops every part at `STOP_USD` ($20 by default).

1. Build the image from the revision under test:

   ```sh
   docker build -t hearth-stress:<tag> --build-arg BUILD_REVISION=$(git rev-parse HEAD) .
   ```

2. Create the scoped AWS identity, as in [`loadtest/live/README.md`](../../loadtest/live/README.md): `aws login`, then `loadtest/live/aws-iam.sh up`.

3. Seed Hearth once, then run the ladders at both sizes and the drill (each command detached, with the same `SESSION`):

   ```sh
   scripts/run-detached.sh run seed -- env SESSION=<id> IMAGE=hearth-stress:<tag> \
     loadtest/compare/aws/compare.sh seed hearth
   scripts/run-detached.sh run s1 -- env SESSION=<id> IMAGE=hearth-stress:<tag> \
     loadtest/compare/aws/compare.sh ramps hearth 1
   scripts/run-detached.sh run s2 -- env SESSION=<id> IMAGE=hearth-stress:<tag> \
     loadtest/compare/aws/compare.sh ramps hearth 2
   scripts/run-detached.sh run drill -- env SESSION=<id> IMAGE=hearth-stress:<tag> \
     loadtest/compare/aws/compare.sh drill
   ```

   `compare.sh ramps hearth 1 refresh create_user` runs only those journeys.

4. Clean up: `compare.sh snapshots`, `compare.sh delete-snapshots <id>...`, then `loadtest/live/aws-iam.sh down`.

The results are in `loadtest/live/results/compare-<id>/` (git-ignored): one JSON per journey and size with every step's verdict, and `summary.md`.
