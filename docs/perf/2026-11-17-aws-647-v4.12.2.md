## Method

**Clean rate.** The marks define the clean rate as the highest ramp step with 0 errors other than Argon2 `503`s, and with p99 under the limit of the journey. This report applies the definition as follows:

- The clean step is the step below the first step that fails. A later step that passes does not count.
- The p99 limits are the budgets of `loadtest/live/ramps.py`: login and mix 1,000 ms, refresh 100 ms, userinfo, admin lookup and introspect 50 ms.
- A step with dropped journeys is not clean.
- For login, every error in these ramps is an Argon2 `503` (`login_submit:503`). So every login step is clean, and the offered rate says nothing. The login rate is therefore the completed logins/s at the highest clean step. The v3.4.0 baseline measured login in the same way (50–56 logins/s).
- For the other journeys, the rate is the offered rate of the clean step.
- For mark 3, the p99 of round C at its clean step is compared with the p99 of round A at the same offered step.

**Correction.** The interim results on v4.12.0 counted Argon2 `503`s as errors for login and the mix. This report does not. With the written definition, round A login and mix and round C login and mix have higher clean rates than the interim comment said.

**Sustained rate.** The tables also give the `Sustained` rate of `ramps.py`: the highest step with at most 1 % errors and p99 in budget. It is for comparison only. No mark uses it.

## Setup

**Servers**

- Rounds A and B: AWS c7i.large, 2 vCPU (1 physical core with hyper-threading), 3,812 MiB RAM, Intel Xeon Platinum 8488C.
- Round C: AWS r7i.large, 2 vCPU, 15,702 MiB RAM, the same CPU.
- Ubuntu 24.04. No swap.
- Disk: EBS gp3 root volume, 3,000 IOPS, 125 MB/s. A synced 4 KiB write takes about 3.3 ms (`dd oflag=dsync`: 2,000 writes in 6.49–6.56 s).
- Every write is fsynced to the write-ahead log (WAL) before the server acknowledges it.
- HTTPS with TLS 1.3 and HTTP/2.

**Data**

| Round | Users | Import | Store on disk after the import |
|---|---|---|---|
| A (refresh rerun) | 1M, 1 realm | 94.4 s (10,589 users/s), 0 failed | 1.7 GB |
| B | 1M, 10 realms of 100k | 73.3 s (13,640 users/s), 0 failed | 1.7 GB |
| C | 10M, 1 realm | 1,168.0 s (8,562 users/s), 0 failed | 15 GB |

**Load generators**

- 2 × AWS c7i.xlarge (4 vCPU, 7,775 MiB each), k6 2.0.0, 1,000 virtual users per generator.
- Open loop: k6 starts journeys at the offered rate, also when the server is slow.
- Before each plan line, the store was restored from the same post-import copy, the page cache was dropped, and Hearth was restarted.

**Units.** The journeys, the mix and the units are the same as in the [v3.4.0 report](2026-10-10-aws-c7i-large.md#units). Server CPU is out of 200 % (2 vCPU).

**Background compaction.** At low load, the round C server uses about 85 percentage points more CPU than round B: 113.7 % against 27.3 % at userinfo 2,000/s, and 116.0 % against 31.1 % at refresh 200/s. Partial SST compactions of 4–7 files run every 20–60 s in each step. Each step restores the same store copy, which was taken while compactions ran, so each step runs the same compactions again. This is the probable cause of the lower round C results. It is not confirmed. Details: #889.

**Restart and crash**

- Clean stop: 0.3 s, result `success`. The log shows `memtable flushed on shutdown`.
- Start to the first `200` from `/readyz`: 127.7 s. Every start in round C took 125.5–125.8 s (the `Startup:` line). On v4.12.0, the same step took 66.0 s, and the `Startup:` line showed about 74.4 s.
- `kill -9` at 300 s of a 900 s mix at 120/s: the start took 116.1 s (v4.12.0: 26.5 s). The server acknowledged 4,645 user creations, and `k6/verify.js` found all 4,645.
- During the start after `kill -9`, the process had up to 8–9 GB of anonymous memory, and RSS reached 15,085 MiB (96.1 % of RAM). After the server was ready, anonymous memory went back to about 0.9 GB.
- The store at start: WAL 223.5 MB, 13 SSTs, 15.0 GB on disk. On v4.12.0: WAL 35.0 MB, 194 SSTs, 8.0 GB. At 1M users, the start time did not change. Details: #888.

**Backup under load (mark 5)**

The mix ran at 120 journeys/s in 3 steps of 900 s. `POST /admin/backup` started at the start of step 2. The plan was set before the runs, at 120/s. That is 40 % of the round C mix clean rate, not the 50 % of the mark.

| Step | Errors | p50 | p99 | RSS |
|---|---|---|---|---|
| 1, no backup | 0.00 % | 19.1 ms | 165.2 ms | 8,625 MiB |
| 2, backup | 2.52 % | 18.8 ms | 379.6 ms | 8,758 MiB |
| 3, after the backup | 1.27 % | 18.4 ms | 154.1 ms | 5,127 MiB |

- The backup took 76.2 s, exit status 0. The archive is 2,270,203,106 bytes (v4.12.0: 174.4 s, 1,411,582,506 bytes).
- At the backup, the write limit refused 1,000 writes and the Argon2 queue refused 303 logins. The `503` errors come from these refusals: `refresh` × 791, `login_submit` × 301, `code_exchange` × 68. Details: #891.
- `userinfo:401` (2,684 in steps 2 and 3) is probably a side effect in the load script: a failed refresh leaves an expired access token. This is not confirmed.
- Memory during the backup stayed at 56 % of RAM. On v4.12.0, the backup took the heap to about 9.6 GB (#866). The streaming backup (#868) holds.

**Restore drill (mark 5)**

`restore-drill.sh` set up a new server, seeded 10M users, made a backup, and restored it into an empty data directory.

| Step | Time |
|---|---|
| Seed: 10M users through `POST /admin/users/import` | 23 min 29 s |
| `POST /admin/backup` | 3 min 57 s (archive 4,935,871,321 bytes) |
| `hearth backup verify` | 40.8 s |
| `hearth backup sign` | 2 min 05 s |
| `hearth backup restore` | stopped by hand at 31 min 50 s |

After 30.2 min, the import pass had read 139 MB of the archive (2.8 %), at about 74 KB/s. The restore process used 5 % CPU and 176 MB RSS, and it waited in `jbd2_log_wait_commit` (the ext4 fsync wait). The restore writes one user per durable commit, about 175 users/s. At that speed, the full restore needs about 18 hours. Each test instance stops itself after 10 hours, so the restore was stopped. 9,694 of 10,010 sampled users were not restored. Details: #887.

The drill also found that its user count check sends an integer cursor to `GET /admin/users` and gets `400 invalid cursor` (#892). The memory of the restore stayed low: the streaming restore (#875) holds.
